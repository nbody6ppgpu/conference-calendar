# Conference calendar — agent instructions

## What this repository is

- `data/conferences.yml` is the single hand-written source of truth: a flat
  `conferences:` list of entries, each with `id`, `title`, `url`, `location`,
  `start_date`, `end_date`, `registration_deadlines`, `abstract_deadlines`,
  `registration_display`, `abstract_display`, and `comments`. Use `""` or `[]`
  for what you don't have — never omit a key.
- The list has exactly two comment markers: `  # Past events` (line 2, first)
  and `  # Conference Calendar`. Entries above the second marker are archived;
  entries below it are active. The markers are layout only —
  `scripts/cleanup_calendar.py` decides placement from each entry's
  `end_date`, and it is the only thing that should move an entry across the
  marker.
- `conference_calendar.md` and the entire `site/` directory (including
  per-meeting ICS files under `site/meetings/`) are generated by
  `scripts/build_calendar.py`. They are git-ignored and must never be
  hand-edited or committed.
- New entries added from an issue get an `id`: a lowercase hyphenated slug of
  the conference name plus its year (e.g. `stars-on-the-run-iii-2026`). It
  must be unique in the file.

## Rules that apply to every task

- Edit only `data/conferences.yml`. Everything else the calendar shows —
  `conference_calendar.md`, `site/`, `site/*.json`, `site/*.ics`, and the
  per-meeting ICS files under `site/meetings/` — is regenerated by
  `scripts/build_calendar.py` and the Pages deployment, so a hand edit there
  is overwritten and a committed one shows up as diff noise. CI asserts that
  an automated run changed exactly this one file.
- For page template or static text changes, edit `scripts/calendar_core.py`
  (`build_index_html` / `build_past_events_html`) and rebuild — never edit
  `site/index.html` or `site/past-events.html` directly.
- Never invent a date. If a deadline is only stated as text such as `TBA`,
  `open`, or `?` — or isn't stated at all — leave the structured date field
  empty and put the text (if any) in `registration_display` /
  `abstract_display` instead. This calendar exists to be trustworthy; a
  plausible-looking guessed date is worse than a blank one, because nothing
  downstream can tell it apart from a real one.
- If an entry has multiple registration or abstract deadlines, represent them
  as structured list items with `label` and `date`.
- Do not fill in or change `comments` unless the user (an issue body, a task
  instruction) explicitly supplied that text. It is authored by humans, not
  discovered by EXPLORE.
- To verify a YAML change, build into a scratch directory so no generated
  file lands in the working tree:

  ```bash
  out="${RUNNER_TEMP:-$(mktemp -d)}"
  python3 scripts/build_calendar.py \
    --markdown-output "$out/conference_calendar.md" \
    --site-dir "$out/site"
  ```

  A non-zero exit means the YAML is malformed — fix it before finishing.
  Never run the bare `python3 scripts/build_calendar.py` outside of a scratch
  directory: its defaults write `conference_calendar.md` and `site/` straight
  into the repository working tree.

## EXPLORE(url)

EXPLORE(url) means: fetch that page and read the conference's own site to
establish `title`, `url`, `location`, `start_date`, `end_date`,
`registration_deadlines`, and `abstract_deadlines`.

If a fact is not on the landing page, follow links reachable from that same
site — typically pages named dates, important dates, registration, abstract
submission, program, venue, or FAQ. Stop after those; if a fact still isn't
stated on the conference's own site, leave the field as it is rather than
guessing where else it might live.

Use only the conference site itself. Do not use a web search engine: a
plausible-looking date from a third-party aggregator is exactly the kind of
error this calendar exists to avoid, and it is not distinguishable from a
real one after the fact. (This is also enforced in automation: the
`WebSearch` tool is not made available to you there.)

Never EXPLORE for the `comments` field — see the shared rule above.

## Mode 1 — Add a conference from an issue

The input is an issue created from the "Add a new meeting" template. Its body
has an "URL link for the meeting" field and a "Comments to show on the
calendar table" field.

- Take the conference URL from the "URL link for the meeting" field and
  EXPLORE it.
- Write `comments` only if the issue's comments field is non-empty — copy it
  as given; that field is the only thing that ever authorizes a `comments`
  value for a new entry.
- Add one new entry to `data/conferences.yml` under `# Conference Calendar`
  with all the fields listed above.
- Verify the build (see the shared rules).
- In your final message, state the new entry's `id` and which fields you
  could not find on the conference site, if any.

## Mode 2 — Monthly cleanup

This mode has two parts, run as two separate commits by the workflow. You
normally only do the second part — the workflow runs the first part itself
before you start.

- **Archive placement** (not your job): a deterministic step already ran
  `python3 scripts/cleanup_calendar.py --today "$CLEANUP_DATE"`, which moves
  every entry whose `end_date` is before `$CLEANUP_DATE` from
  `# Conference Calendar` into `# Past events`, and a later `--check` step
  fails the job if you edit that result by hand. Do not move entries between
  the past and active parts of the file yourself, and do not recompute
  today's date — use `$CLEANUP_DATE` throughout.
- **Metadata enrichment** (your job): for each entry after the
  `# Conference Calendar` marker whose `start_date`, `end_date`,
  `registration_deadlines`, or `abstract_deadlines` is empty or holds no real
  date, EXPLORE its `url` and fill in what the source supports. If you can't
  find a fact, leave the field as it is — do not guess, and do not write
  `TBA` yourself; a source that hasn't announced a date yet will simply be
  checked again next month.
- Verify the build after your edits (see the shared rules).
- In your final message, list which entries you enriched and which fields
  you filled, and say explicitly if you changed nothing.

The full task instructions for whichever commit you're producing are in
`.github/prompts/monthly-calendar-cleanup.md` (archive step, informational
only) or `.github/prompts/metadata-enrichment.md` (enrichment step, this is
the one you actually run as an agent).

## Mode 3 — Reviewer (invoked by hand)

A factual verification and repair pass over only the conference entries
changed in the current PR or working tree — not a full-table cleanup. It is
no longer triggered automatically; a human invokes it with
`.github/prompts/conference-data-reviewer.md`, which holds the full
instructions. Follow that file; the shared rules above still apply.
